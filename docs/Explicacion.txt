 PARTE 0 · ¿DE QUÉ VA ESTE PROYECTO? (leer esto primero)
══════════════════════════════════════════════════════════════════════════════

0.1 EL PROBLEMA QUE RESUELVE
─────────────────────────────
En negocios pequeños, bodegas y oficinas, las cuentas por pagar se revisan a
mano: alguien toma la factura en papel, la compara contra la orden de compra
en una hoja de cálculo y decide si está bien o hay discrepancias. Eso es
lento y propenso a errores: facturas duplicadas, montos que no coinciden,
vencimientos que se pasan por alto.

0.2 LA IDEA EN UNA FRASE
────────────────────────
"Le tomas una FOTO a la factura con el celular, y el sistema solo te dice
si está APROBADA o tiene DISCREPANCIAS — sin que nadie la teclee."

0.3 LAS 5 TECNOLOGÍAS Y EL PAPEL DE CADA UNA
────────────────────────────────────────────
Imagina una oficina automatizada donde cada empleado habla un idioma
distinto pero todos trabajan en el mismo edificio:

  ┌──────────────┬───────────────────────────────────────────────────────┐
  │ Tecnología   │ Su trabajo en el proyecto                              │
  ├──────────────┼───────────────────────────────────────────────────────┤
  │ Android/Java │ El RECEPCIONISTA: toma la foto y la entrega al        │
  │ (la app)     │ edificio. También mostrará los resultados.             │
  │ PHP + MySQL  │ La OFICINA CENTRAL: recibe la foto, la guarda en el   │
  │ (API + BD)   │ archivero (MySQL) y coordina a todos los especialistas│
  │ Python       │ EL LECTOR (OCR): "lee" la imagen y extrae el texto    │
  │              │ (proveedor, fecha, monto, folio).                     │
  │ C (compilado)│ EL ANALISTA DE RIESGO: con el monto y el historial    │
  │              │ del proveedor calcula un % de riesgo (alza sospechosa)│
  │ Prolog       │ EL AUDITOR LÓGICO: con reglas decide APROBADA o       │
  │              │ DISCREPANCIA comparando factura vs orden de compra.   │
  └──────────────┴───────────────────────────────────────────────────────┘

0.4 EL FLUJO COMPLETO (el objetivo final del MVP)
─────────────────────────────────────────────────
  1. Abres la app → eliges contra qué orden de compra vas a facturar.
  2. Tomas foto de la factura.
  3. La app la envía por internet (red local) al servidor PHP.
  4. PHP la guarda en disco + registra "Pendiente" en MySQL.
  5. (Sprint 3-4) Python lee la imagen → C calcula riesgo → Prolog decide.
  6. PHP guarda el veredicto en MySQL.
  7. La app muestra: ✅ Aprobada / ⚠️ Con Discrepancia.

0.5 VOCABULARIO QUE USAREMOS (por si suena raro)
────────────────────────────────────────────────
  · API ....... "ventanilla" del servidor: URLs a las que la app pide cosas.
  · Endpoint .. una URL concreta de la API (ej: /api/facturas.php).
  · JSON ...... formato de texto para intercambiar datos {"clave": "valor"}.
  · Base64 .... forma de convertir una FOTO (binario) a TEXTO para poder
                enviarla dentro de un JSON.
  · OCR ....... reconocimiento óptico de caracteres = "leer" texto de imágenes.
  · Seed ...... datos de ejemplo con los que nace la base de datos.
  · Sprint .... bloque de trabajo de ~1 semana con entrega verificable.
  · Checkpoint (C1..C4) ... prueba que demuestra que el sprint funciona.
  · MVP ....... versión mínima que ya demuestra el valor del producto.

 PARTE 2 · SPRINT 1 — LA BASE: BASE DE DATOS + API (28/09/2026)
══════════════════════════════════════════════════════════════════════════════

Meta del sprint: que desde Postman (una app para probar APIs) se pudiera

2.1 ¿QUÉ ES LARAGON Y POR QUÉ LO USAMOS?
─────────────────────────────────────────
Laragon instala en un solo paquete Apache + MySQL + PHP, es decir, todo el
"servidor" de internet en tu propia PC (C:\laragon). Con Laragon iniciado,
tu computadora sirve páginas web en http://localhost. El proyecto se publicó
en C:\laragon\www\cpp, de modo que la API vive en http://localhost/cpp/api/.
Ventaja: todo corre LOCAL, sin pagar hosting ni servicios en la nube.

2.2 LA BASE DE DATOS (database/seed.sql)
────────────────────────────────────────
Un archivo .sql es una lista de instrucciones para MySQL. Este crea la base
"cpp" y 4 tablas, y además inserta datos de ejemplo (por eso se llama "seed"
= semilla: lo siembras todo de una vez). Es re-ejecutable: si lo importas
otra vez, borra y recrea todo (solo para desarrollo).

  TABLA               QUÉ GUARDA                      POR QUÉ EXISTE
  ─────────────────────────────────────────────────────────────────────
  usuarios            admin, capturista, revisor      El login llega en v1.0;
                      (todos con password demo1234)   por ahora solo semilla.
  ordenes_compra      OC-001 Papelería Central $5,000 La factura se compara
                      OC-002 Ferretería $8,500        CONTRA estas órdenes.
                      OC-003 Oficinas del Norte $3,200.50
  facturas            cada foto enviada: estado,      El corazón del sistema:
                      ruta_imagen, monto, folio,      aquí nace "Pendiente" y
                      riesgo, motivo_discrepancia     aquí muere "Aprobada"/
                                                       "Con Discrepancia".
  historial_proveedor montos anteriores por proveedor  Alimenta al módulo C:
                      (ej: 6 compras de Papelería      sin historial no se
                      entre $3,600 y $4,200)          puede detectar alzas.

  Detalles finos que ya quedaron listos para los sprints futuros:
  · La columna facturas.procesado_en servirá para medir el KPI "procesar
    en ≤ 30 segundos" (comparándola con creado_en).
  · Las columnas folio, riesgo, proveedor_detectado esperan ser llenadas
    por Python y C en el Sprint 3.
  · La FK (llave foránea) facturas.orden_id → ordenes_compra.id impide
    registrar una factura contra una orden inexistente (integridad).
  · El historial fue calculado a propósito: Papelería Central promedia
    ~$3,941, así una factura de $4,850 (+23%) dará riesgo BAJO y una de
    $6,200 (+57%) dará riesgo ALTO. Sirve para la demo final.

2.3 LOS ARCHIVOS PHP DE LA API (carpeta api/)
────────────────────────────────────────────
La API son 5 archivos pequeños, cada uno con UNA responsabilidad:

  config.php ... EL PANEL DE AJUSTES. Todo lo que puede cambiar según la
                 máquina vive aquí: usuario/contraseña de MySQL, carpeta de
                 subidas, umbral de riesgo (40%) y las rutas FUTURAS de
                 python/swipl/GCC. Si algo cambia, se edita SOLO este archivo.

  db.php ........ EL PUENTE A MYSQL. Abre la conexión con PDO (la forma
                 segura de hablar con bases de datos en PHP). Usa el patrón
                 "singleton": crea UNA sola conexión y la reutiliza siempre,
                 en lugar de abrir una nueva por cada consulta.

  responder.php . EL MEGÁFONO. Toda respuesta de la API sale con el mismo
                 formato JSON para que la app Android siempre la entienda:
                   { "codigo": "OK"|"ERROR_...", "mensaje": "...", "datos": {...} }
                 "codigo" es la palabra clave (OK, ERROR_VALIDACION...),
                 "mensaje" es texto humano, "datos" trae la información.

  facturas.php .. LA VENTANILLA PRINCIPAL (endpoint más importante):
                   POST /api/facturas.php  → recibir una foto y registrar
                                             la factura como "Pendiente".
                   GET  /api/facturas.php  → listar facturas (más recientes
                                             primero), con filtro opcional
                                             ?estado=Pendiente
                   GET  ...?id=5           → detalle de una factura.

  ordenes.php ... LA VENTANILLA DE APOYO: GET devuelve las órdenes de compra
                   (para que la app llene su lista desplegable) y, si pides
                   ?id=1, incluye el promedio del historial del proveedor —
                   exactamente el dato que el módulo C necesitará en S3.

2.4 ASÍ FUNCIONA UN POST DE FACTURA, PASO A PASO (facturas.php)
───────────────────────────────────────────────────────────────
Cuando la app (o Postman) envía {"orden_id":1, "imagen_base64":"..."}:

   1. Se lee el cuerpo JSON y se valida que orden_id sea entero ≥ 1.
   2. Se pregunta a MySQL si esa orden existe (si no → error 422 y ya).
   3. Se valida que imagen_base64 venga; si trae prefijo "data:image/..."
      (formato data URI) se le quita, dejando solo el Base64 puro.
   4. Se comprueba el tamaño: máximo ~8 MB decodificados (el Base64 infla
      el texto ~40%, por eso se multiplica por 1.4 al medir).
   5. base64_decode converte el TEXTO de vuelta a FOTO (bytes binarios).
   6. TRUCO DE SEGURIDAD: no se confía en lo que el cliente dice que es;
      se revisa la "firma de bytes" del archivo (FF D8 FF = JPEG real,
      89 50 4E 47 = PNG real). Si no es ninguno → error 415.
   7. Se genera nombre único: factura_20260928_191530_a3f2c1b7.jpg
      (fecha + 8 caracteres aleatorios) y se guarda en uploads/.
   8. INSERT en la tabla facturas: orden_id + ruta de la imagen + estado
      'Pendiente'. MySQL devuelve el id nuevo de la factura.
   9. Se responde 201 (creado) con el id, el estado y la orden.
  Nota: si el texto OCR→riesgo→conciliación fallara algún día, la factura
  NUNCA se pierde: queda como "Pendiente" para reintentar (decisión RNF-5).

2.5 EL PROBLEMA DEL PUERTO 3306 (y cómo se resolvió)
────────────────────────────────────────────────────
Síntoma: phpMyAdmin no conectaba. Causa: en el equipo había instalados
MySQL como servicios de Windows (MySQL80, MySQL81, MySQL84 en
C:\Program Files\MySQL). Solo UN programa puede usar el puerto 3306
("la puerta" por la que se habla con MySQL); cuando el servicio externo
arrancaba primero, el MySQL de Laragon se quedaba fuera.

Solución aplicada (como administrador):
    net stop MySQL84                     → detener el intruso
    Set-Service MySQL84 -StartupType Manual  → que no arranque solo

Regla para siempre: este proyecto usa EXCLUSIVAMENTE el MySQL de Laragon
(C:\laragon\bin\mysql\mysql-8.0.30-winx64, datos en C:\laragon\data\mysql-8,
usuario root sin contraseña). Ver el puerto ocupado:
    Get-NetTCPConnection -State Listen | ? LocalPort -eq 3306

 PARTE 3 · SPRINT 2 — LA APP ANDROID "CAPTURA" (28/09/2026)
══════════════════════════════════════════════════════════════════════════════

Meta del sprint: que una foto REAL tomada con el celular llegue al servidor
y apareciera como "Pendiente" en MySQL. Eso es el checkpoint C2. ✔ LOGRADO
Todo el proyecto Android vive en C:\CPP\android (app "com.cpp.captura").

3.1 QUÉ HACE LA APP, EN PALABRAS SIMPLES
────────────────────────────────────────
Tiene UNA pantalla con: un campo de texto "Servidor" (la IP de tu PC),
una lista desplegable de órdenes de compra, un espacio para la foto, y dos
botones: [Tomar foto] y [Enviar factura]. Al abrirla:
   1. Descarga las órdenes desde GET /api/ordenes.php y llena el spinner.
   2. Tomas la foto → se ve en pantalla (vista previa).
   3. Enviar → "✅ Factura Nº X registrada como «Pendiente»" en verde.
La IP queda GUARDADA (SharedPreferences), no se teclea cada vez.

3.2 LAS PIEZAS CLAVE EXPLICADAS
───────────────────────────────
  · Volley (librería de Google) ... hace las peticiones HTTP por ti, en
    segundo plano (sin congelar la pantalla). Usamos JsonObjectRequest
    tanto para pedir las órdenes como para enviar la factura.

  · La cámara (MediaStore.ACTION_IMAGE_CAPTURE) ... no programamos una
    cámara: pedimos al sistema "ábreme la cámara" con un Intent. Android
    abre la app de cámara que ya tenga el celular y nos devuelve la foto.

  · FileProvider ... la cámara necesita un lugar donde DEJAR la foto. Por
    seguridad, Android ya no deja escribir en cualquier carpeta, así que
    la app presta una carpeta propia de caché mediante un "FileProvider"
    (configurado en AndroidManifest.xml + res/xml/file_paths.xml). Así no
    hacemos falta permisos de almacenamiento, solo el de CÁMARA.

  · Permiso en tiempo de ejecución ... desde Android 6 los permisos
    "peligrosos" (cámara, ubicación...) se piden EN VIVO con un diálogo:
    "¿Permitir que CPP tome fotos?". El código lo pide y espera el
    resultado antes de abrir la cámara.

  · Compresión inteligente ... una foto de celular moderna pesa 3-8 MB.
    La app la reescala a lado mayor ≤1600 px y la comprime a JPEG calidad
    85 → queda en ~200-600 KB. Detalle técnico: usa inSampleSize para
    decodificar la imagen YA reducida (si decodificaras completo y luego
    reescalaras, la memoria explotaría). El envío es rápido y la calidad
    sigue siendo suficiente para el OCR del Sprint 3.

  · Base64 ... internet/JSON transporta TEXTO, no binario. Base64
    convierte los bytes de la foto en letras (por eso "infla" ~40%).
    El servidor hace la operación inversa (base64_decode).

  · usesCleartextTraffic="true" ... Android 9+ bloquea por defecto el
    HTTP sin cifrado. Nuestra API corre en http:// (Laragon local), así
    que hay que permitirlo explícitamente en el AndroidManifest.

3.3 ¿POR QUÉ 10.0.2.2? (la IP del emulador, explicación)
─────────────────────────────────────────────────────────
Dentro del emulador, "localhost" significa EL EMULADOR MISMO, no tu PC.
Google reserva 10.0.2.2 como alias de "la máquina que hospeda al emulador"
(tu PC). Por eso: emulador → 10.0.2.2 · móvil físico → la IP LAN real del
PC (ipconfig → IPv4, ej. 192.168.1.20) + regla de firewall para el puerto
80 si no conecta:
    netsh advfirewall firewall add rule name="CPP Apache 80" dir=in
        action=allow protocol=TCP localport=80

 PARTE 5 · LO QUE VIENE, EXPLICADO (Sprint 3 y 4)
══════════════════════════════════════════════════════════════════════════════

SPRINT 3 — LOS TRES MOTORES (carpeta nueva motores/)
Se llaman "motores" porque son programas independientes que PHP encenderá
uno tras otro. Cada uno se prueba SOLO, por línea de comandos (checkpoint
C3), y ya tiene su "contrato" (qué debe imprimir exactamente):

  · procesar_factura.py (OCR, Python)
      Recibe la ruta de una imagen y "lee" la factura. Usará pytesseract
      (necesita instalar Tesseract-OCR en Windows) o EasyOCR. Imprime:
        {"proveedor":"...","fecha":"YYYY-MM-DD","monto":4850.00,"folio":"F-123"}
      Antes de programarlo hay que hacer el "spike": probar ambos OCR con
      5 fotos reales y elegir el mejor (tarea pendiente).

  · clasificador_riesgo.c (C, compilado con GCC)
      Recibe 2 números: el monto de la factura y el promedio histórico del
      proveedor. Devuelve un % de riesgo: si la factura se dispara por
      ENCIMA del historial (alza sospechosa), el riesgo sube. Ej: imprime
      "37.5". Regla del proyecto: riesgo < 40% = confiable.

  · regla.pl (Prolog, corre con SWI-Prolog)
      Se le "declaran" hechos (la factura extraída y la orden de compra) y
      con reglas lógicas concluye: imprime "APROBADA" o
      "DISCREPANCIA:<motivo>" (ej: monto excede la orden, proveedor no
      coincide, riesgo alto). Prolog brilla aquí: expresar reglas de
      negocio como lógica pura.

SPRINT 4 — INTEGRACIÓN Y DEMO
PHP orquesta todo: tras recibir la factura llama con shell_exec a los 3
motores, les pasa datos validados (¡seguridad: escapeshellarg para que
nadie inyecte comandos!), guarda el veredicto en MySQL y la app muestra
una lista con badges de color por estado. Checkpoint C4 = demo completa.

DATOS QUE YA ESPERAN A LOS MOTORES:
  · api/config.php ya tiene las constantes PYTHON_BIN, SWIPL_BIN y las
    rutas motores/*.py, *.exe, *.pl.
  · ordenes.php?id=1 ya devuelve historial_promedio del proveedor.
  · La BD ya tiene historial sembrado para calcular riesgos creíbles.

 PARTE 6 · EL SPIKE OCR EXPLICADO (30/09/2026) — ¿pytesseract o EasyOCR?
═══════════════════════════════════════════════════════════════════════════════

6.1 ¿QUÉ ES UN "SPIKE"?
──────────────────────
Un spike es un experimento corto que se hace ANTES de comprometerse con
una tecnología, para responder una pregunta concreta (aquí: "¿qué OCR
usamos?"). El MVP dejó este spike pendiente desde el Sprint 1 y era el
paso 0 del Sprint 3. Se resolvió HOY: GANA PYTESSERACT.

6.2 LO QUE SE INSTALÓ (y aprendizajes de la instalación)
────────────────────────────────────────────────────────
  · Python 3.12.10 ... no había Python (solo el "alias" del Microsoft
    Store, que no es Python de verdad). Instalado con winget. Detalle
    curioso: la instalación silenciosa NO incluye pip; se reparó con
    "python -m ensurepip --upgrade".
  · Tesseract-OCR 5.4.0 ... el "cerebro" OCR: pytesseract es solo el
    puente de Python hacia este .exe. Instalado con winget (build de
    UB-Mannheim). Trae solo inglés; se le bajó el modelo ESPAÑOL
    (spa.traineddata, 17.4 MB) del repositorio oficial tessdata.
  · EasyOCR 1.7.2 ...... el competidor (redes neuronales). Arrastra
    PyTorch (~2 GB descomprimidos). Solo CPU en este equipo.
  · GCC MinGW 6.3.0 y SWI-Prolog ya existían — se verificaron sus rutas
    y quedaron fijadas en api/config.php (era pendiente de S6 Bitácora).

6.3 ¿Y LAS 5 FOTOS REALES? → SINTÉTICAS PERO DEGRADADAS
──────────────────────────────────────────────────────
El spike pedía fotos reales, pero en uploads/ solo había 3 JPEG "dummy"
de 209 bytes (las pruebas C2 validaron conectividad, no contenido).
Solución: generar_fotos_prueba.py DIBUJA 5 facturas con los datos del
seed (mismos proveedores y montos: $4,850 riesgo bajo, $6,200 alto...) y
luego las "estropea" como una foto real: rotación 2-4.5°, inclinación,
desenfoque, ruido, brillo/contraste variables, JPEG 82-90 y 1600 px de
lado mayor — exactamente lo que envía la app Android. Cuando existan
fotos reales: copiarlas a fotos/, actualizar verdad.json y re-ejecutar
spike_ocr.py (acepta --fotos CARPETA).

6.4 CÓMO SE COMPARÓ (para que el duelo sea justo)
─────────────────────────────────────────────────
Cada OCR devuelve TEXTO plano, no campos. Para no favorecer a ninguno,
ambos pasan por el MISMO extractor (extraer_campos de spike_ocr.py):
regex que buscan folio, fecha, monto (línea "TOTAL") y proveedor
(primera línea con letras). Se puntúa contra verdad.json (4 campos × 5

 PARTE 7 · LOS TRES MOTORES EXPLICADOS (30/09/2026, tarde) — C3 superado
═══════════════════════════════════════════════════════════════════════════════

Con la decisión del spike (pytesseract) se programaron los 3 motores y se
pasó el checkpoint C3. Cada motor es un programa INDEPENDIENTE que PHP
"encenderá" uno tras otro en el Sprint 4 (por eso cada uno se prueba solo,

7.1 MOTOR 1 · procesar_factura.py (Python + pytesseract) — EL LECTOR
────────────────────────────────────────────────────────────────────
    CLI    : python procesar_factura.py <ruta_imagen>
    Salida : UNA línea JSON {"proveedor","fecha","monto","folio"}
  Reutiliza tal cual extraer_campos(), la misma lógica que logró 100% en el
  spike: las regex buscan la línea "TOTAL" para el monto, "Folio" para el
  folio, la primera fecha del texto y la primera línea con letras para el
  proveedor. Detalles pensados para el Sprint 4:
  · Un campo que no se pueda leer viaja como null (decidir qué hacer con
    los nulls será de PHP, no del OCR).
  · Si la imagen no existe o el OCR revienta: {"error":"..."} y código de
    salida 1 → PHP sabrá que falló y la factura queda "Pendiente" (RNF-5).
  · Verificado: las 5 fotos del spike → 5/5 JSON correctos.

7.2 MOTOR 2 · clasificador_riesgo.c (C, compilado con GCC) — EL ANALISTA
─────────────────────────────────────────────────────────────────────────
    CLI    : clasificador_riesgo <monto_factura> <promedio_historial>
    Salida : el % de riesgo con un decimal (ej. 27.3)
  La fórmula se diseñó para poder EXPLICARLA en una defensa del proyecto:
    desviación d = (monto − promedio) / promedio × 100
    · d ≥ 0 (factura POR ENCIMA del historial): riesgo = 10 + 0.75·d
    · d < 0 (por debajo): riesgo = 10 + 0.25·d (baja menos de lo que sube)
    · tope [0,100]; sin historial → 50.0 (conservador: no aprueba solo)
  La base 10 es el "riesgo residual normal". Con el seed de la BD:
    4,850 vs 3,941.67 (+23.1%) → 27.3 BAJO  |  6,200 (+57.3%) → 53.0 ALTO.
  Se compila con el GCC MinGW del equipo; el .exe queda FUERA de git
  (motores/.gitignore): si alguien clona el repo, debe recompilarlo.

7.3 MOTOR 3 · regla.pl (SWI-Prolog) — EL AUDITOR LÓGICO
───────────────────────────────────────────────────────
    CLI    : swipl regla.pl <id> <folio> <monto> <fecha> <proveedor>
                            <riesgo> <monto_autorizado>
                            <proveedor_orden> <fecha_orden>
    Salida : APROBADA  ó  DISCREPANCIA:<motivo>
  Aquí Prolog muestra su ventaja: las reglas de negocio se escriben CASI
  como se dirían en español, y el orden de las cláusulas con "!" (corte)
  define la prioridad del motivo:
    1) monto > autorizado ................ DISCREPANCIA:MONTO_EXCEDE_ORDEN
    2) riesgo ≥ 40 ....................... DISCREPANCIA:RIESGO_ALTO
    3) proveedor distinto ................ DISCREPANCIA:PROVEEDOR_NO_COINCIDE
    4) fecha fuera de [orden−15d, orden+90d] → DISCREPANCIA:FECHA_FUERA_DE_RANGO
    5) si nada falla ..................... APROBADA
  Dos detalles dignos de explicar:
  · PROVEEDOR TOLERANTE: el OCR lee "PAPELERÍA CENTRAL, S.A. DE C.V." y la
    BD guarda "Papelería Central". Se normaliza todo (mayúsculas, sin
    acentos, solo letras/números) y se pide que un prefijo de 8 caracteres
    de uno aparezca contenido en el otro: los acentos y el ", S.A." no
    rompen la comparación.
  · FECHAS COMPARABLES: "2026-09-20" se convierte a número de día juliano
    (fórmula de ~4 líneas) para poder sumar/restar tolerancias en días.

8.1 EL NUEVO JEFE DE ORQUESTA: api/procesar.php (RF-B3)
────────────────────────────────────────────────────
PHP ya sabía RECIBIR fotos (facturas.php) y CONSULTAR (GET); ahora también
PROCESA. procesar.php acepta ?id=N (una factura Pendiente) o SIN id (TODAS
las Pendientes, para reintentos en bloque) y ejecuta, en orden, los 3
motores por línea de comandos con shell_exec — como se ensayó en C3, pero
automático:
   1) OCR ....... python procesar_factura.py <imagen>  → JSON
   2) Riesgo .... clasificador_riesgo.exe <monto> <promedio>  → "27.3"
   3) Conciliar . swipl regla.pl <factura + orden + riesgo>  → APROBADA/…
   4) UPDATE facturas SET ..., procesado_en=NOW()  (KPI-1)
Si todo sale bien devuelve el veredicto CON medidores: duracion_pipeline_s
(~1.2 s de media) y segundos_desde_creacion (el KPI-1 real, ≤ 30 s). Ese
último se calcula con TIMESTAMPDIFF DENTRO de MySQL: como PHP y MySQL
pueden vivir en zonas horarias distintas, si PHP midiera con su propio
reloj el resultado saldría desfasado horas (pasó y se corrigió así).

8.2 LA SEGURIDAD PROMETIDA (R3/RM4 → RNF-4)
───────────────────────────────────────────
Ejecutar comandos con datos "del mundo" es peligroso: si alguien fingiera
que el monto es "4850 & borrar_todo", un PHP ingenuo lo ejecutaría. Las
defensas aplicadas:
   · escapeshellarg() envuelve CADA argumento dinámico: las comillas y
     símbolos del atacante quedan convertidos en texto inofensivo.
   · Cast numérico: monto/promedio/riesgo pasan por (float) y salen con
     sprintf("%.2F") — solo pueden ser NÚMEROS, nunca comandos.
   · La fecha se valida con regex YYYY-MM-DD y el folio se recorta.
   · Los PROVEEDORES se convierten a ASCII (iconv TRANSLIT) antes de
     pasarlos a Prolog: cmd.exe lee la línea de comandos con la página de
     códigos ANSI y los bytes UTF-8 de "Ferretería" llegarían manguados,
     rompiendo la comparación tolerante de regla.pl. ASCII es "idempotente"
     para su normaliza() (normalizar algo ya normalizado no lo cambia).
   · Aprendizaje en vivo: la teoría decía "envuelve el comando completo en
     comillas extra para cmd.exe"; la PRÁCTICA (pruebas A/B/C/D) mostró que
     popen de PHP ya arma bien la línea y que el wrap extra la ROMPE. Quedó
     documentado en el código para no recaer.

8.3 CUANDO ALGO FALLA: NADA SE PIERDE (RNF-5)
─────────────────────────────────────────────
Regla del PRD: "el fallo de un módulo no pierde la factura". Implementación:
si un motor no responde lo esperado, procesar.php NO TOCA MySQL y la factura
sigue «Pendiente», con diagnóstico amable:
   · 500 MOTOR_*_FALLO — el motor reventó (probado con una imagen corrupta

Además es IDEMPOTENTE: reprocesar una factura ya procesada devuelve
YA_PROCESADA con su estado, no la vuelve a tocar.

9.1 EL "TEATRO" DE LA DEMO (preparación)
─────────────────────────────────────────
Un móvil físico ve al PC por la IP del Wi-Fi (192.168.1.48), no por
"localhost". Hizo falta: Laragon arrancado (mysqld + Apache a mano), una
regla del firewall de Windows abriendo el puerto 80 (netsh advfirewall),

CURL DESDE EL TELÉFONO (adb shell) antes de culpar a la app. Las fotos
demo se copiaron por adb a /sdcard/Download del móvil.

9.2 HOTFIX 0.4.1 — LA CÁMARA "INVISIBLE" (visibilidad de paquetes)
───────────────────────────────────────────────────────────────────
Síntoma: al pulsar «Tomar foto», "el dispositivo no tiene ninguna app de
cámara"... ¡sí la tenía! Causa: desde Android 11, una app con targetSdk
30+ NO VE el resto de las apps salvo que lo declare en el manifest con
<queries>. Sin eso, resolveActivity() devuelve null aunque la cámara
exista. Solución: declarar el intent android.media.action.IMAGE_CAPTURE
en <queries>. Lección: el emulador suele tener "todo visible" y no
reproduce este filtro; solo el móvil real lo destapó.

9.3 HOTFIX 0.4.2 — POTENCIAS DE 2 (inSampleSize) VS REESCALADO EXACTO
──────────────────────────────────────────────────────────────────────
Síntoma: la foto de la cámara llegaba al servidor a 1024×461 px en vez
de 1600: el OCR no podía leerla. Causa: decodificar() solo usaba
inSampleSize, que reduce EN POTENCIAS DE 2 (1, 2, 4, 8…): una foto de
4128 px cae a 1024, tirando el 36% de la resolución objetivo. Solución:
muestrear hasta ≤2×maxLado y luego Bitmap.createScaledBitmap al tamaño
EXACTO. Lección: "reducir un poco" y "reducir a la mitad" no son lo
mismo cuando el consumidor es un OCR.

9.4 HOTFIX 0.4.3 — EXIF: LA FOTO QUE LLEGA "ACOSTADA"
─────────────────────────────────────────────────────
Síntoma: foto tomada en vertical → la app la mostraba horizontal. Causa:
muchas cámaras guardan los píxeles girados y anotan la rotación en el
metadato EXIF Orientation... que BitmapFactory IGNORA. Solución:
orientarSegunExif() (androidx.exifinterface 1.3.7) rota el bitmap ANTES
de reescalar; el JPEG enviado viaja ya vertical, sin depender de
metadatos que el servidor no sabría interpretar.

9.5 RF-M3 ADELANTADO — EL BOTÓN «ELEGIR DE GALERÍA»
───────────────────────────────────────────────────
El PRD traía RF-M3 (elegir imagen de la galería) diferido a la v1.0; la
demo lo adelantó porque fotografiar el MONITOR baja demasiado la
resolución. Cómo funciona: Intent.ACTION_GET_CONTENT tipo image/* abre
el selector del sistema SIN permisos de almacenamiento (devuelve un
content:// con lectura temporal); la app copia el stream a su caché y de
ahí sigue el MISMO pipeline que la cámara (EXIF → 1600 px → JPEG 85 →
Base64). Un solo pipeline, dos fuentes: buen diseño para la v1.0.

9.6 LA LECCIÓN MÁS GRANDE: LA FUENTE DE LA IMAGEN MANDA
────────────────────────────────────────────────────────
Las primeras pruebas fallaron por «FECHA_FUERA_DE_RANGO»: el OCR leía
"2025" donde decía "2026" y "F-1004" donde decía "F-1001". ¿Los motores
estaban mal? NO: las imágenes habían pasado por un CHAT (WhatsApp), que
las re-comprimió a ~473×631 px. Con el archivo ORIGINAL (1202×1600) el
OCR leyó TODO, incluso después del JPEG-85 de la app (verificado en el
PC). Moraleja para el producto real: la calidad de captura es parte del
requisito; en la v1.0 conviene avisar al usuario ("imagen de baja
resolución") y/o guiar la captura (marco, enfoque).

(capturista envía, revisor consulta, admin administra) y el admin crea
usuarios y órdenes desde el móvil, sin abrir phpMyAdmin.

11.2 CÓMO FUNCIONA UN LOGIN CON TOKEN (la idea en 6 pasos)
──────────────────────────────────────────────────────────
 1. La app manda usuario+contraseña a POST /api/sesion.php (por HTTPS
    iría cifrado; aquí es red local de demo).
 2. PHP busca el usuario en la tabla `usuarios` y verifica la clave.
 3. Si está bien, genera un TOKEN: 64 caracteres hex aleatorios
    (random_bytes de PHP: impredecible). Es como una llave de hotel.
 4. Guarda la llave en la tabla nueva `sesiones` con fecha de expiración
    (8 h, configurable en config.php: SESION_TTL_HORAS).
 5. Devuelve el token a la app, que lo guarda en SharedPreferences
    (clase Sesion) y lo manda en la cabecera "X-CPP-Token" de TODAS
    las peticiones siguientes.
 6. Cada endpoint protegido llama a requerirAutenticacion() (¿la llave
    existe y no expiró?) o requerirRol([...]) (¿quién entra puede?).
    Sin llave → 401 NO_AUTENTICADO; con llave pero rol insuficiente →
    403 ROL_NO_PERMITIDO. La app, al ver 401, borra la sesión y regresa
    al login automáticamente.

11.3 LAS DOS GENERACIONES DE CONTRASEÑAS (migración sin dolor)
──────────────────────────────────────────────────────────────
El seed del MVP guardaba la clave como SHA-256 en hex (CHAR 64). La v1.0
usa bcrypt (password_hash de PHP), que es MÁS seguro (lento a propósito
y con "sal" incorporada) pero produce hashes de ~60 caracteres → la
columna pasó a VARCHAR(255) (migrar_v1.sql sube el esquema sin borrar
datos). Para no obligar a cambiar claves, sesion.php acepta AMBOS
formatos: los 3 usuarios semilla siguen entrando con demo1234 y los
usuarios que cree el admin ya nacen con bcrypt.

11.4 EL CRUD Y SUS REGLAS DE NEGOCIO (api/usuarios.php y ordenes.php)
─────────────────────────────────────────────────────────────────────
 · CREAR usuario: nombre + usuario único (409 USUARIO_DUPLICADO si ya
   existe) + clave de 6+ caracteres + rol válido. Nunca se devuelve el
   hash en las respuestas.
 · EDITAR: nombre, rol, clave (vacío = no tocarla) y activo. Baja LÓGICA
   (activo=0): el historial no se pierde; no hay DELETE físico.
 · Regla ULTIMO_ADMIN: si al editar te fueras a quedar sin ningún admin
   activo, la API responde 409 y no aplica el cambio (evita el clásico
   "me encerré fuera del sistema").
 · Órdenes: crear/editar código (único), proveedor, monto>0, fecha real
   (checkdate) y estado abierta/cerrada. «Cerrar» es su baja lógica:
   las facturas existentes la referencian por FK y no se rompe nada.
 · Solo el admin llega a estos POST; los demás roles reciben 403.

 PARTE 12 · SPRINT 6 "FIREBASE" — EL PROVEEDOR SE ENTERA SOLO (15/10/2026)
═══════════════════════════════════════════════════════════════════════════════

12.1 LA IDEA NUEVA
──────────────────
Hasta el Sprint 5, cuando un capturista subía una factura, solo se
enteraba quien abriera la app a revisar. Pero hay un tercero interesado:
el PROVEEDOR, que quiere saber «¿ya recibieron mi factura?». El problema:
el proveedor NO tiene (ni debe necesitar) una cuenta del sistema. La
solución elegida: FIREBASE (los servidores de Google) como «radar y
avisos» — el proveedor toca «🏬 Soy proveedor» en el login, elige su
nombre de una lista y su teléfono queda suscrito a los avisos de sus
facturas. (Este sprint es alcance NUEVO, RF-F1..F4; el «S6 inteligencia»
planeado pasó a S7.)

12.2 FIREBASE NO REEMPLAZA NADA (decisión clave)
───────────────────────────────────────────────
MySQL+PHP+Python+C+Prolog siguen siendo el CEREBRO (guardan y deciden).
Firebase solo hace dos cosas que MySQL no sabe hacer bien:
  · FIRESTORE: base de datos de Google que AVISA al instante cuando algo
    cambia (un «oyente» en la app se dispara solo, sin consultar cada
    rato). Aquí se escriben los documentos de `notificaciones` y también
    `clientes` (quién entra a la app) y `proveedores` (qué teléfono
    escucha a qué proveedor).
  · FCM (Firebase Cloud Messaging): envía el PUSH, la notificación que
    aparece aunque la app esté CERRADA (la clásica bajadita de la barra
    superior). Se envía a un TEMA por proveedor, no a un teléfono fijo:
    cualquier teléfono suscrito al tema lo recibe.

12.3 EL CIRCUITO COMPLETO DE UN AVISO
─────────────────────────────────────
  1. El capturista sube la factura (igual que siempre).
  2. facturas.php la guarda en MySQL (esto NUNCA cambia) y luego llama a
     fb_notificar_factura() — BEST-EFFORT: si Firebase falla, la factura
     ya está a salvo y el error solo queda en el log del servidor.
  3. PHP escribe un documento en Firestore `notificaciones` → si el
     proveedor tiene la app ABIERTA, el oyente de ProveedorActivity lo
     muestra AL INSTANTE (sin botón de actualizar).
  4. PHP además envía el push FCM al tema proveedor_<slug> → si la app
     está CERRADA, Android lo muestra solo; al tocarlo se abre el buzón.

12.4 EL SLUG: QUE PHP Y JAVA DIGAN LO MISMO
───────────────────────────────────────────
El tema FCM y el documento deben coincidir aunque el nombre venga con
acentos y espacios («Ferretería El Tornillo»). Ambos lados normalizan el
nombre EXACTAMENTE IGUAL a un «slug»: sin acentos, minúsculas, solo
letras/números → «ferreteriaeltornillo». fb_slug() (PHP) y slug() (Java)
son espejos: si alguien cambia uno, HAY que cambiar el otro.

12.5 SEGURIDAD Y SECRETOS
─────────────────────────
  · Para escribir en Firebase, PHP se autentica como «cuenta de servicio»
    (un robot con llave privada). La llave vive en
    api/firebase-service-account.json — es un SECRETO que permite enviar
    push a nombre del proyecto, así que .gitignore la EXCLUYE del repo
    (quien clone el repo debe conseguirla aparte; sin ella todo sigue
    funcionando, solo que sin avisos). El JWT se firma con openssl (que
    PHP ya trae) y el token de acceso se CACHEA ~50 min: cero
    dependencias PHP nuevas.
  · La app usa AUTH ANÓNIMA de Firebase: las reglas de Firestore exigen
    «app legítima» sin pedirle cuenta Google a nadie.
  · proveedores.php es PÚBLICO a propósito: solo expone NOMBRES de
    proveedores (los que ya están en órdenes de compra), nada de montos
    ni folios. En producción se endurecería (p. ej. código por proveedor).

12.6 LA EXCEPCIÓN A LA REGLA DE NO-DEPENDENCIAS
───────────────────────────────────────────────
El proyecto se enorgullecía de no agregar librerías… pero Firebase en
Android no se puede «escribir a mano»: se aprobó (usuario) agregar SOLO
firebase-bom 33.1.2 + firestore + messaging + auth y el plugin
google-services 4.4.2, que inyecta google-services.json al build (ese
archivo SÍ va en git: solo identifica el proyecto, no es secreto).

14.2 QUÉ SE LE AGREGÓ A LA BASE DE DATOS

el conflicto se resolvió a mano). La «Pendiente» —aún sin veredicto del
pipeline— no se puede pagar: primero debe pasar por OCR→riesgo→Prolog.

  · Desde la foto se paga: «💰 Marcar como pagada» (o «↩️ Devolver» si te

  · En PAGADAS, chips para revisar CLASIFICADAS: Todas · ✅ Aprobadas ·

14.4 UNA REGLA QUE CAMBIÓ A MEDIAS (y por qué)
─────────────────────────────────────────────
Primero se programó «solo se pagan Aprobadas». Al probarlo saltó la
contradicción: si nunca se pagan discrepancias, la pestaña de pagadas
jamás tendría nada que clasificar (que era justo el requisito). En la vida
real una discrepancia se resuelve por fuera y LUEGO se paga. Regla final:
se paga todo lo que TENGA veredicto; la «Pendiente» queda fuera.

14.6 ¿QUIÉN ES EL CLIENTE? (y el «Crear cuenta» genérico)
────────────────────────────────────────────────────────
Pregunta del usuario: si la cuenta puede ser de «cliente», ¿quién es el
cliente: el admin, el capturista o el revisor? Respuesta: el cliente es
LA EMPRESA QUE PAGA, y sus tres roles internos son su PERSONAL:
  📷 capturista — sube las facturas que recibe la empresa;
  🔍 revisor — consulta y audita (solo lectura);
  👑 admin — el jefe: administra usuarios y órdenes, y también paga.
Por eso el botón se volvió «🆕 Crear cuenta» con elección de tipo:
  · 🏬 PROVEEDOR → registro público (rol de mínimos: solo ve SU negocio);
  · 🏢 CLIENTE → la app EXPLICA los tres roles y aclara que esas cuentas
    las crea un administrador (⚙️ Administración → Usuarios). ¿Por qué no
    autoregistro también para el cliente? Porque cualquiera podría
    auto-darse acceso a TODAS las finanzas de la empresa: el capturista,
    revisor y admin ven todo; el proveedor solo lo suyo. El registro
    público solo puede dar el rol más pequeño.

14.7 CADA CLIENTE VE SOLO SUS CUENTAS (S8.2)
────────────────────────────────────────────

empresas: solo SUS cuentas — las que le faltan por pagar y las que ya
pagó — para ponerse al corriente; cada cliente puede tener múltiples
cuentas». Solución: cada factura recuerda QUIÉN la subió (columna
subida_por). Así:
  · 💰 Cuentas por pagar muestra ÚNICAMENTE lo que el usuario que entró
    subió: sus pendientes y sus pagadas (nadie paga la cuenta de otro:
    la API contesta 403 FACTURA_DE_OTRO_CLIENTE).
  · 📋 Ver facturas: capturista y revisor también ven solo lo suyo; el
    ADMIN conserva la vista completa (alguien tiene que gestionar el
    sistema: órdenes, usuarios, todo).
  · El proveedor sigue en su mundo: sus avisos y su buzón (S6/S7).
La prueba lo dejó claro: el capturista (que subió las facturas de la
demo) ve «POR PAGAR (14) / PAGADAS (7)»; el revisor (que nunca subió
nada) ve «0/0 — ¡Al día! 🎉». Misma pantalla, datos distintos: cada
quien lo suyo.

──────────────────────────────────────────────────
"¿Esta factura ya me la habían mandado?" no puede responderla Prolog
solo: Prolog únicamente ve lo que le pasan. El trabajo se reparte:
  · procesar.php (PRE-CHECK): antes de calcular el riesgo busca en MySQL
    otra factura con el MISMO FOLIO o con la misma TERNA monto+fecha+
    proveedor (el proveedor se compara por SLUG — la normalización de
    Firebase — para que «Papeleria» == «Papelería»).
  · regla.pl (REGLA 0): recibe un nuevo 10.º argumento si|no; si es "si"
    responde DISCREPANCIA:FACTURA_DUPLICADA ANTES que cualquier otra regla
    (un duplicado no se aprueba aunque todo lo demás calce). El contrato
    pasó de 9 a 10 argumentos; llamarlo con 9 ahora da ARGUMENTOS_INVALIDOS.
La respuesta trae duplicada_de=<id de la original> y el listado muestra su
consejo 💡 («revisa la original para no pagarla dos veces»). Nota de
operación: la detección es GLOBAL, así que la regresión del trío §9.2
exige base limpia (por eso el checkpoint respalda con mysqldump y trunca
facturas antes de correr).

15.3 EL OCR YA NO TIRA NADA (RF-D5)
────────────────────────────────────
Antes solo se guardaban los 4 campos extraídos. Ahora procesar_factura.py
añade "texto" (el OCR crudo) a su JSON — contrato ADITIVO: un consumidor
viejo que no lo mire sigue funcionando. La tabla facturas gana la columna
texto_ocr MEDIUMTEXT (migrar_v1.sql §7) y el DETALLE (GET facturas.php?
id=N) lo expone: sirve para auditar QUÉ leyó el OCR cuando un veredicto
se discute. El listado no lo arrastra (pesaría de más).

15.4 LOS CHIPS POR FIN FILTRAN (RF-M6)
───────────────────────────────────────
Los chips ✅/⚠️/⏳ del listado eran un resumen bonito; ahora son BOTONES:
un tap deja en pantalla solo ese estado (el chip activo se pinta relleno,
con texto blanco) y otro tap sobre el mismo chip lo quita. Los conteos
siguen siendo del TOTAL (el filtro no engaña) y una línea explica
«🔎 Filtro: Con Discrepancia · 3 de 12 facturas». El filtrado es LOCAL:
la API ya sabía ?estado= desde el Sprint 1.

15.5 CUÁNDO VENCE UNA CUENTA (RF-M7)
─────────────────────────────────────
¿De dónde sale la "fecha límite" que el PRD menciona sin definirla?
Decisión documentada: fecha del documento de la factura (o la de subida
si el OCR no la leyó) + 30 días (PAGO_DIAS_LIMITE en config.php). La
calcula el SERVIDOR — pagos.php añade fecha_limite/dias_restantes/
vence_pronto a cada fila — para que la regla viva en un solo lado; la
app solo colorea: en ROJO «⏰ Vence en N día(s)» o «🚨 VENCIDA hace N»
cuando quedan 3 días o menos (ALERTA_VENCE_EN_DIAS), y el diálogo de
pago muestra «📅 Límite de pago». Detalle de demo: la factura de prueba
quedó con 3 días justos → sale roja al instante.

15.6 EL FIX QUE NADIE VIO LLEGAR (S8.3 en la app)
──────────────────────────────────────────────────
Al auditar el repo saltó una INCONSISTENCIA: pagos.php ya no aceptaba
"pagar" seco (el S8.3 exige "comprobar" CON foto del comprobante), pero
la app 0.12 seguía mandando "pagar" → el botón de pago del móvil estaba
ROTO desde el 16/10 (esa sesión dejó BD+API listos y la app a medias,
sin documentar). Arreglo: el botón ahora es «📷 Adjuntar comprobante y
pagar» → abre la GALERÍA (ACTION_GET_CONTENT, sin permisos) → comprime
igual que una factura (≤1600 px, JPEG 85, Base64) → POST comprobar con
imagen_base64. El servidor guarda la foto como evidencia_*.jpg y solo
entonces marca pagada: sin evidencia no hay pago. De paso, en POR PAGAR
una «Con Discrepancia» ya no dice «✅ Aprobada»: muestra su motivo real.

AJUSTE S9.1 (mismo día, a pedido del usuario): en POR PAGAR el diálogo
NO muestra NINGUNA foto — solo los datos de la cuenta y la instrucción
«📎 para pasarla a PAGADAS adjunta la foto de tu comprobante». La lógica
ya era esa en el servidor; lo que pasaba es que la app enseñaba primero
la foto de la FACTURA, que confunde (no es lo que prueba el pago). Ahora
la única foto del flujo es la del COMPROBANTE que sube el cliente, y la
foto de la factura se revisa en PAGADAS (el requisito original del S8:
clasificar lo pagado por veredicto). Flujo final: pendiente (solo datos)
→ «📷 Adjuntar comprobante y pagar» → galería → el servidor valida → la
cuenta aparece en PAGADAS. App 0.13.1-v1 (vc 20).

16.1 ¿QUÉ SE PIDIÓ Y QUÉ SIGNIFICA?
───────────────────────────────────
Dos pedidos del usuario cambiaron la arquitectura de un plumazo:
  1) «Que ya no necesitemos Laragon para las pruebas»: el «servidor»
     (Apache+MySQL+PHP) existía SOLO para la demo local. Firebase
     (gratis en su capa Spark) lo reemplaza por servicios en la nube.
  2) «Que las órdenes no necesiten una IP; que las suba el proveedor
     para notificar a los clientes lo que deben»: antes el cliente
     tecleaba la IP del PC con Laragon para alcanzar la API. Ahora el
     PROVEEDOR sube la cuenta («lo que te deben») a Firestore indicando
     el CORREO del cliente, y el teléfono del cliente la recibe SOLO
     (oyente en tiempo real). Nadie teclea ninguna IP.

16.2 LAS PIEZAS DE FIREBASE QUE USAMOS
──────────────────────────────────────
  · AUTH (Email/Password): el correo ES el usuario. Login con
    signInWithEmailAndPassword; el google-services.json (commiteado)
    identifica el proyecto cpp-facturas. Sin token propio ni IP.
  · FIRESTORE (base de datos en la nube): colecciones —
    usuarios/{uid} (perfil: rol, negocio) · ordenes (las cuentas que
    sube el proveedor: clienteCorreo, monto, fechaLimite, estado) ·
    facturas (los veredictos del pipeline) · notificaciones y
    proveedores (las del S6). Los oyentes (addSnapshotListener)
    repintan la pantalla solos cuando algo cambia.
  · STORAGE: las fotos — facturas/<timestamp>.jpg y el comprobante
    de pago comprobantes/<ordenId>.jpg. Pagar = adjuntar la foto:
    sin evidencia no hay pago (igual que S8.3/S9.1).
  · ADMIN por REST: la clave de servicio (SECRETO, fuera de git)
    permite a los scripts PHP de CONSOLA crear usuarios y sembrar
    datos sin Laragon (semilla_firebase.php).

16.3 ¿Y EL PIPELINE? SE PORTÓ AL TELÉFONO (Motores.java)
────────────────────────────────────────────────────────
Firebase no puede ejecutar Python/C/Prolog. Solución: portar los 3
motores a Java DENTRO de la app, con resultados equivalentes:
  · OCR ......... ML Kit de Google lee el texto EN EL DISPOSITIVO
                  (modelo latino, sin internet) y extraerCampos()
                  aplica las MISMAS regex del spike de Python.
  · RIESGO ...... clasificadorRiesgo() replica la fórmula del C
                  (base 10 + 0.75×alza / 0.25×baja, tope [0,100]).
  · CONCILIACIÓN . conciliar() replica regla.pl cláusula por cláusula
                  (0 duplicado → 1 monto → 2 riesgo → 3 proveedor
                  tolerante → 4 fecha [−15,+90] días julianos). El
                  pre-check de duplicados consulta Firestore (antes
                  MySQL). El HISTÓRICO para el riesgo también sale de
                  Firestore (promedio de las últimas facturas).
Los originales (motores/*.py/.c/.pl) quedan como REFERENCIA académica
y para la demo con Laragon.
