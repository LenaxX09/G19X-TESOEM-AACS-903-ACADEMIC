SECCIÓN 5 · ARQUITECTURA Y DECISIONES IMPORTANTES
────────────────────────────────────────────────────────────────────────────────

  Flujo objetivo (MVP):
    [App Android] --foto Base64--> [API PHP] --> [MySQL]
                                        |--(S3)--> Python OCR (texto → JSON)
                                        |--(S3)--> C riesgo (porcentaje)
                                        |--(S3)--> Prolog (APROBADA/DISCREPANCIA)
    [App Android] <--estado final-- [PHP actualiza MySQL]

  Decisiones tomadas:
    - Envío de imagen en Base64 JSON (RF-M4 simplificado; multipart → v1.1).
    - Estados de factura: Pendiente / Aprobada / Con Discrepancia.
    - UMBRAL_RIESGO = 40 % (riesgo < 40 ⇒ aprobable) — configurable en
      api/config.php.
    - Contratos de los motores FIJADOS ANTES de programarlos (principio
      contract-first, MVP §6.4):
        Python (stdout 1 línea): {"proveedor":"...","fecha":"YYYY-MM-DD",
                                 "monto":1234.56,"folio":"..."}
        C (stdout 1 línea):      37.5        ← % de riesgo
        Prolog (stdout 1 línea): APROBADA  ó  DISCREPANCIA:<motivo>
    - Si un motor falla, la factura NO se pierde: queda "Pendiente" (RNF-5).
    - Seguridad R3/RM4: al llegar S4, cast numérico y saneo de todo lo que
      pase a shell_exec (usar escapeshellarg, nunca texto directo).
    - MySQL: SIEMPRE el de Laragon; servicios MySQL8x de Windows en Manual.

  ★ SPRINT 3 — "MOTORES" (carpeta nueva: C:\CPP\motores\)

    0) SPIKE OCR: instalar/probar pytesseract vs EasyOCR con 5 fotos reales
       y elegir uno. (pytesseract necesita Tesseract-OCR instalado en Windows
       + variable de entorno; EasyOCR es más pesado de instalar.)
    1) motores/procesar_factura.py
       CLI: python procesar_factura.py <ruta_imagen>
       Salida (1 línea JSON): {"proveedor","fecha","monto","folio"}
    2) motores/clasificador_riesgo.c  → compilar con GCC a .exe
       CLI: clasificador_riesgo <monto> <promedio_historial>
       Salida: porcentaje de riesgo (ej. 37.5). Detecta alza vs historial.
    3) motores/regla.pl  (SWI-Prolog)
       Hechos: factura(folio, monto, fecha, proveedor) + orden de compra.
       Predicado conciliar(IdOrden). Salida: APROBADA | DISCREPANCIA:<motivo>.
       Reglas: monto ≤ autorizado, riesgo < 40, coincidencia proveedor/fecha.
    4) CHECKPOINT C3: probar cada módulo por CLI con datos reales de las
       OC-001..OC-003 y satisfacer los contratos de la Sección 5.

      actualizar factura en MySQL, y lista con badges en Android (C4 = demo).

    ordenes.php?id= devuelve historial_promedio por proveedor; seed tiene
    historial sintético para el módulo C.
